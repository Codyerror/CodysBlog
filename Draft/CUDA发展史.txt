CUDA 发展史：从三角形到张量

日期：2026-11-05
标签：CUDA, GPU, NVIDIA, 并行计算, 技术史
摘要：从 2D 加速卡到 Blackwell，CUDA 不是一次灵光乍现，而是图形硬件、可编程着色器与生态飞轮共同推出来的结果。本文沿着 GPU 前史、G80、深度学习拐点与现代软件栈回看这条路径，也讨论它的争议。

一、在显卡出现之前

最早的个人计算机没有“显卡”这个概念。所谓显示，不过是一块把字符送到屏幕上的电路。人们盯着黑底绿字或者白底黑字，屏幕上滚动的是数字、字母和命令行。那时候的“图形”是字符拼出来的，分辨率低，颜色也少，看久了确实枯燥。

改变从游戏和窗口化系统开始。游戏要对色彩、分辨率和矢量加速提出更高的要求，窗口系统则要求屏幕能同时容纳多个界面。这些需求一点点把图形从字符里拽出来：先是低分辨率的 2D 画面，再是高分辨率、色彩丰富的 2D 加速，最后是三维。早期使用电脑的人多是爱好硬核、崇尚键盘和代码的发烧友，图形化的潮流一开始并不快；但一旦游戏和操作系统把“好看的画面”变成刚需，硬件的方向就被改写了。

1995 年，NVIDIA 推出第一款产品 NV1；1997 年，RIVA 128 把 128 位 3D 图形带进主流 PC；1999 年 8 月，GeForce 256 登场，NVIDIA 把它称作“industry's first GPU”。这个说法是营销定义，不是技术史上的绝对起点，但它抓住了一个真实的变化：GPU 开始把变换、光照和渲染从 CPU 手里接过来，成为一个独立的图形计算部件。

二、三角形、光栅化，以及 CPU 为什么不适合

计算机里的 3D 图像，本质上是一个个三角形拼出来的。对人来说，测量三角形的边长和位置并不难；对计算机来说，问题是怎么把这些三角形变成屏幕上的像素。答案就是光栅化：先判断每个三角形覆盖了哪些像素块，再计算顶点位置，把插值信息交给后续的着色阶段，最后得到光照和颜色。我们看到的一块完整画面，其实是由无数个小像素块拼起来的。

这件事的性质很特别：单个像素的计算不复杂，但像素数量极大，而且每个像素的运算彼此独立。换句话说，渲染是低复杂度、高并行的计算。

CPU 的硬件不是为这种负载长的。为了提高单线程性能，CPU 堆了分支预测器、乱序执行单元、大容量缓存、复杂的指令调度逻辑。这些东西在处理不规则的控制流、数据库查询、操作系统调度时非常值钱，但面对“几百万个像素都做同一套简单运算”的场景，它们的大量面积和功耗用在了错误的地方。CPU 像少数几个全能的专家，GPU 像一大群只会做简单运算、但能同时开工的工人。渲染要的不是专家，而是工人数量。

GPU 的设计哲学也由此确定：用大量简单核心换吞吐，用并行换延迟。一个线程等内存的时候，就切换到另一个线程；一个 warp 停住的时候，就换另一个 warp 上来。它不追求单线程跑得多快，而是追求同一时刻有多少工作在做。

三、可编程着色器：CUDA 的偶然前史

早期的 3D 管线是固定的：顶点变换、光照、纹理混合，每一步都写死在硬件里。2001 年 2 月，GeForce 3 发布，NVIDIA 称它是行业里第一个可编程 GPU；配合 DirectX 8 的顶点着色器和像素着色器，开发者第一次可以把一小段程序送到 GPU 上执行。

这一步很关键，但它还不是通用计算。着色器仍然被关在图形管线里：能访问的资源有限，分支和循环很弱，不能随意读写内存，输出也必须回到图形流程。你可以让 GPU 算光照，但不能很自然地让它算矩阵乘法。

可研究者不这么想。既然 GPU 里已经有大量浮点单元，为什么不把数据伪装成纹理、把计算伪装成渲染？于是从 2000 年代中期开始，BrookGPU、Sh 这一类 GPGPU 尝试出现了：它们绕开图形 API 的限制，用纹理和像素着色器做通用计算。这些尝试在今天看来很笨拙，但它们证明了一件事：GPU 的算力可以不属于图形。

历史有时候不是被规划出来的，而是被一群想跑得更快的人挤出来的。NVIDIA 并不是从 1995 年就想好了 CUDA；是可编程着色器先造出了一大片浮点算力，学术界和工业界再证明这片算力有人要用，CUDA 才有机会从“图形卡的附加功能”变成“GPU 的操作系统”。

四、G80 与 CUDA：把显卡变成计算机

2006 年 11 月 8 日，G80 架构的 GeForce 8800 GTX 发布。它有 128 个流处理器，采用统一着色器设计：同一批核心可以按负载分配给顶点、像素、几何和物理计算，不再像过去那样把顶点单元和像素单元分开。NVIDIA 后来把这代架构称为 Tesla。

也是在这一代硬件上，CUDA 第一次亮相。这里有个容易混淆的时间差：CUDA 随 G80 在 2006 年出现，而 CUDA Toolkit 1.0 的正式发布是在 2007 年 6 月。很多资料把“CUDA 诞生”写成 2006 或 2007，其实分别指这两个节点。本文按“2006 年随 G80 亮相、2007 年工具包正式发布”来写。

CUDA 真正带来的变化，不是给 C 语言加了一层语法糖，而是把 GPU 的并行结构直接暴露给程序员：kernel 在 grid 上启动，grid 由 block 组成，block 里是一组线程；线程有私有的寄存器和局部内存，block 内可以用共享内存和同步屏障。程序员第一次可以用“线程”而不是“像素”来思考 GPU。


__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}


这段代码没有顶点，没有纹理，也没有光照。它只是把两个数组相加，却完整地展示了 CUDA 的世界观：一个 kernel 启动成千上万个线程，每个线程拿自己的编号去处理一小块数据。

G80 最重要的不是“128”这个数字，而是它把“一个线程”变成了程序员可以调度的单位。硬件层面，这靠的是 SIMT：32 个线程组成一个 warp，同一时刻执行同一条指令。这样做能把控制和数据路径做得很窄，代价是分支分歧——同一个 warp 里如果一半线程走 if、一半走 else，两条路径只能串行执行，部分 lane 空转。CUDA 的性能问题，从第一天起就和“怎么让一个 warp 里的线程尽量走同一条路”绑在一起。

五、生态飞轮：真正的护城河

如果 CUDA 只是“能用 C 写 GPU”，它不会变成今天这样。真正让它站住脚的，是围绕它长出来的一整套东西。

最底层是 CUDA Toolkit：nvcc 编译器、运行时、驱动 API、调试器、性能分析工具、文档和示例。往上一层是库：cuBLAS 做矩阵运算，cuFFT 做傅里叶变换，cuSPARSE 做稀疏矩阵，cuSOLVER 做线性代数，Thrust 和 CUB 提供并行算法与基础构件。再往上，是 cuDNN、NCCL、TensorRT 这些面向深度学习和分布式训练的库。再往上，是 PyTorch、TensorFlow、JAX 这些框架。

于是飞轮转起来了：开发者用 CUDA 写代码，库和框架把 CUDA 作为默认后端，论文和产品继续产生新的 CUDA 代码，NVIDIA 卖卡之后再把这些钱投回工具链、文档和生态，下一批开发者又更愿意从 CUDA 开始。

[配图] CUDA 生态飞轮
文件：/images/cuda-history/06-ecosystem-flywheel.png

图 2：开发者、库、应用与出货构成一个自我强化的循环；飞轮越快，单点性能差距越难撼动它。

这个飞轮还有一层很少被单独提起的燃料：兼容性。PTX 作为虚拟指令集，让旧代码有机会在新一代 GPU 上重新 JIT；驱动和运行时又尽量保证老程序还能跑。你写的 CUDA 代码越老，越能感受到这种承诺的价值；但越依赖这种承诺，也越难离开 NVIDIA 的硬件。

这就是 CUDA 护城河的真相：它不是某一项技术，而是“默认路径”。当所有人都默认用 CUDA，默认用 cuDNN，默认在 NVIDIA 的卡上复现论文，默认在遇到问题时搜索 CUDA 的报错，竞争就已经不只在芯片层面发生了。

六、深度学习的拐点

GPU 不是为深度学习发明的，深度学习也不是为 GPU 发明的。两者在 2012 年撞上了。

2012 年的 ImageNet 竞赛上，AlexNet 用两块 GTX 580 3GB 显卡训练了五到六天，把卷积神经网络推到了当时最好的精度。这个结果的说服力不在于“GPU 比 CPU 快多少”，而在于它证明了一套足够大的神经网络可以在可接受的时间里训练出来。深度学习需要的大量矩阵乘法、卷积和归约，恰好是 GPU 最擅长的事情。

2014 年，cuDNN 发布。它把卷积、池化、归一化、激活这些深度学习常用算子做成了高度优化的库，框架不用再自己手写 kernel。2015 年 TensorFlow 开源，2016 年 PyTorch 发布，深度学习框架开始把 CUDA 和 cuDNN 当成默认后端。再到 2016 年，NVIDIA 推出 DGX-1，八块 P100 通过 NVLink 连接；黄仁勋把第一台 DGX-1 送到 OpenAI。2017 年 Transformer 论文出现，2020 年 GPT-3 把参数规模推上千亿。每一步都在把“算力需求”往上抬一层。

[配图] AI 算力需求与架构代际
文件：/images/cuda-history/05-ai-compute.png

图 3：2012 年以后，训练算力需求与架构代际同步抬升。曲线只表达量级方向，纵轴不对应任何具体 FLOPS 数字。

NVIDIA 在这一轮里赢的，不只是浮点峰值。AMD 和 Intel 也有算力，也有 GPU，也在做加速器；但 CUDA 这边有 cuDNN、cuBLAS、NCCL，有成熟的 profiler 和调试器，有框架的第一时间适配，有论文作者直接可复现的代码。硬件可以追一代，软件生态要追很多年。

七、架构代际：从 Tesla 到 Blackwell

把这条线摊开看，GPU 架构的演进并不是每年挤一点牙膏，而是应用需求在倒逼硬件：先是图形，再是 HPC，再是深度学习，最后是大模型。

| 年份 | 架构 | 代表产品 | 当时新增了什么 |
| --- | --- | --- | --- |
| 2006 | Tesla | G80 / GeForce 8800 GTX | 统一着色器、CUDA 编程模型 |
| 2010 | Fermi | GF100 | 面向通用计算的 SM 与缓存体系 |
| 2012 | Kepler | GK110 | 能效提升、动态并行 |
| 2014 | Maxwell | GM204 | 每瓦性能与更精简的 SM |
| 2016 | Pascal | P100 | NVLink、HBM2 |
| 2017 | Volta | V100 | Tensor Core、独立线程调度 |
| 2018 | Turing | TU102 | RT Core、Tensor Core |
| 2020 | Ampere | A100 | TF32、结构化稀疏 |
| 2022 | Hopper | GH100 | Transformer Engine、异步拷贝 |
| 2024 | Blackwell | B200 | FP4、GB200 超级芯片 |

图 4：硬件节点在上、软件与生态节点在下。时间线不是一张显卡发布表，而是一条“硬件能力被软件不断兑现”的路径。

读这张表要注意一个坑：架构代号和产品名经常被混着用。Tesla 既是 2006 年的架构名，也是后来 NVIDIA 面向数据中心的 GPU 品牌名；Volta 之后的 V100、A100、H100、B200 又是产品名。不同资料对“发布”和“出货”的口径也不一致，本文统一取公开发布的年份，Blackwell 之后的路线不在本文展开。

从 Tesla 到 Volta，GPU 的主线是“把更多通用计算做进来”；从 Volta 到 Blackwell，主线变成了“把矩阵乘法和低精度计算做进硬件”。Tensor Core 和 RT Core 的出现，说明 NVIDIA 已经不再把 GPU 当成单纯的图形处理器，而是当成一个可以按工作负载重新配置的加速器。

八、CUDA 软件栈到底由什么组成

很多人以为 CUDA 就是 nvcc 加几个 API。实际上，它是一套从应用一直铺到晶体管的分层系统。

[配图] CUDA 软件栈分层
文件：/images/cuda-history/03-cuda-stack.png

图 5：从框架、领域库、Runtime、PTX、SASS 到驱动与硬件。越往上越稳定，越往下越接近具体架构。

最上面是应用和框架，中间是 cuDNN、cuBLAS、NCCL 这些领域库，再往下是 CUDA Runtime 和 Driver API。多数开发者停在这一层：写 C++ 或 Python，调库，偶尔写一个 kernel。再往下是 PTX，一种虚拟指令集；同一个 PTX 可以在新架构上 JIT，所以旧代码有机会跨代运行。最下面是 SASS，真正的 GPU 机器码，和具体架构绑定，换卡就要重新生成。

这套分层解释了 CUDA 的兼容承诺为什么重要，也解释了它为什么难以被替代：兼容发生在 Runtime 和 PTX 这两层，而性能发生在 SASS 和硬件那一层。你可以把源码搬走，但很难把调优过的 SASS 一起搬走。

再往下看，是显存层级。寄存器最快、容量最小，每个线程私有；共享内存和 L1 在每个 SM 内共享；L2 由整颗 GPU 共享；再往下是 HBM 或 GDDR 全局显存；最后是经 PCIe 或 NVLink 访问的主机内存。容量、带宽、延迟三者在这里做取舍。

[配图] CUDA 显存层级
文件：/images/cuda-history/04-memory-hierarchy.png

图 6：寄存器、共享内存/L1、L2、全局显存与主机内存构成的金字塔；右侧是一个 warp 连续访问与跨步访问的差别。

很多“GPU 跑不快”的代码，问题不在算力，而在数据搬运。一个 warp 的 32 个线程如果访问连续地址，请求可以合并成少量内存事务；如果地址跨步，请求就会被拆成多次，带宽在等待里被浪费。共享内存的 bank conflict、寄存器溢出、occupancy 过低，都是同一类问题：你没有把数据放到离计算最近的地方。

工具也是这套栈的一部分。Nsight Systems 看时间线，Nsight Compute 看 kernel 内部的指标，cuda-gdb 调试，Compute Sanitizer 查内存越界和竞争。会用这些工具的人，和只会 nvidia-smi 看占用率的人，解决同一个性能问题的速度完全不一样。

九、竞争与反思

CUDA 不是没有对手，只是对手很难在“整套栈”上同时追上。

2008 年 12 月，Khronos 发布 OpenCL 1.0。它由 Apple 最初推动，目标是跨厂商、跨设备的开放计算标准。OpenCL 的问题不是“不开放”，而是“开放不等于好用”：不同厂商的实现质量参差，性能可移植性很难保证，写一个复杂的 kernel 需要大量样板代码。它证明了开放标准可以存在，但没能证明开放标准一定能把开发者从 CUDA 手里拿走。

2016 年 4 月，AMD 发布 ROCm 1.0，走的是另一条路：开源、贴近 CUDA 的编程模型、用 HIP 把 CUDA 源码迁到 AMD GPU。HIPIFY 工具可以把不少 CUDA 代码机械地翻译成 HIP，这降低了迁移的第一步。但“能编译”不等于“能跑好”：库的覆盖、工具的成熟度、硬件适配范围、框架的支持深度，都要重新补。MI300X 这类产品在纸面算力上已经很有竞争力，但 ROCm 仍然要面对一个老问题——生态系统不是靠一次发布会补齐的。

Intel 的 oneAPI 走的是更高层的抽象：用 SYCL 做单源 C++ 异构编程，让同一份代码面向 CPU、GPU 和加速器。SYCL 1.2 在 2015 年定稿，SYCL 2020 进一步把模型标准化；oneAPI 的正式工具包在 2020 年底发布。这条路在理念上更干净，但落地同样受限于硬件节奏、库的覆盖和开发者惯性。

还有一类东西叫“CUDA 兼容层”。HIP 是源码级的迁移，ZLUDA 这类社区项目则尝试在二进制层把 CUDA 调用翻译到别的 GPU 上。它们能降低“第一次跑起来”的成本，但降不下“最后一次调优”的成本：性能特征、调试体验、边缘算子、版本兼容，仍然要一处一处补。兼容层是桥，不是家。

所以我的判断是：CUDA 是事实标准，但不是开放标准。它的优势不只是 API，而是库、工具、文档、人才和历史代码共同构成的默认路径；它的争议也不只是“闭源”，而是这种默认路径带来的议价权、供应风险和路径依赖。锁定的另一面是承诺：NVIDIA 用兼容性换信任，用信任换锁定。对用户来说，这不是纯坏事，但把全部筹码押在一家厂商身上，从来都不是没有代价的。

近几年，竞争开始往 CUDA 之上移动。Triton 这类更高层的 kernel DSL 把一部分 CUDA C++ 的工作抬高了一层，PyTorch 2.x 的编译栈也在减少手写 kernel 的比例。但抽象层再高，最终还是要落到某个厂商的后端。真正被争夺的，仍然是“默认路径”这四个字。

十、结语

CUDA 的历史，表面是软件史，底层是硬件史，中间是生态史。

从 NV1 到 GeForce 256，GPU 先解决了“怎么把三角形画到屏幕上”；从 GeForce 3 到 G80，可编程着色器把 GPU 变成了一片可以编程的浮点阵列；从 CUDA 1.0 到 cuDNN，再到 DGX-1 和 Blackwell，软件栈又把这片阵列变成了深度学习的基础设施。

这条路径不是谁在 1995 年就规划好的。它是图形需求、硬件能力、学术研究和商业竞争一层层挤出来的。CUDA 抓住了那个窗口，然后用十八年的库、工具和兼容性，把窗口变成了护城河。

下一代竞争，可能发生在 CUDA 之上，而不是 CUDA 之内。真正值得观察的，不是哪家厂商能在纸面上多出几 TFLOPS，而是谁能把“写代码、调性能、复现论文、部署模型”这条链路做得足够顺。护城河从来不是浮点峰值，而是让人不想离开的那条默认路径。
