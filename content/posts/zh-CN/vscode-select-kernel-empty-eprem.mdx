## 起因

之前学习 python 的时候经常使用 Jupyter，交互式的页面用起来特别舒服，方便排查每一句代码的问题，比自己设置断点 debug 好用多了。现在想做一些 python 的教案，自己做一些小 demo。

结果打开 VS Code 发现无法运行 ipynb 文件了。

## 遇到的问题

我在 VS Code 1.145.0 里打开 ipynb 文件，点右上角的 Select Kernel，列表一片空白，一个可选条目都没有。

`%APPDATA%\jupyter\kernels` 下我自定义的 kernelspec 明明还在。手动输入环境名也没用，即便我打对了名字，也无法选择任何一个内核。

## 艰难坎坷的排查弯路

我的第一反应时我 VS code 的扩展没更新，我去扩展一看，是最新版本。

那是不是版本太新了，和我的 Jupyter 版本对不上呢，我又排查半天，删除又重装 Jupyter 的扩展。依旧无效。

那会不会是我 VS Code 的版本问题，我最近从右键通过 VS Code 打开各种文件都会卡住，只能从 VS Code 的窗口打开才行。（此时已初现端倪）

于是我干脆直接卸载 VS Code，直接重装，看看能不能行。结果还是不行。

看了其他的博客，说是我的环境里没有 ipykernel，所以 VS Code 扫不到 kernel。而且 ipykernel 的版本不能太新，可能出现错配的问题。

好吧，那我就在虚拟环境中安装 ipykernel 6.4.0，还是不行，出现报错。

```text
File "...\ipykernel\iostream.py", line 9, in <module>
    from imp import lock_held as import_lock_held
ModuleNotFoundError: No module named 'imp'
```

一看，我的 venv 环境是 Python 3.12，移除了 `imp` 模块，而 ipykernel 6.4.0 还在使用 `imp` 模块。

这倒不难整，更新版本就可以了。于是我把 ipykernel 升到 7.4.0，顺带提升了 ipython 9.18.1、jupyter_client 8.10.0，再用这个 venv 的解释器重新注册 kernelspec。

终于要结束了，内核这一层终于能用了。我用 jupyter_client 按 kernelspec 名字启动内核。

然后执行一个单元，返回 `ok`，测试能否正常启动内核。都成功了。

正当我兴高采烈打开 VS Code 打算开写讲义的时候，Select Kernel 还是空的。

力竭了，兄弟，真力竭了。

看到空空如也的列表，为啥 Select Kernel 列表啥都没有，明明内核能正常启动。

## 原因显现！

这时我才想到，扩展宿主得通过读 .vscode 才能启动，是不是我的 .vscode 有问题，之前右键通过 VS Code 打不开文件可能也是这个问题。

我打开 `exthost.log`，看到了这一段：

```text
[info] ExtensionService#_doActivateExtension ms-toolsai.jupyter, activationEvent: 'onNotebook:jupyter-notebook'
[error] Activating extension ms-toolsai.jupyter failed due to an error:
[error] Error: EPERM: operation not permitted, stat 'c:\Users\<user>\.vscode'
```

可恶，gitlens、sqltools、claude-code、remote-wsl 都在报 EPERM。也就是说所有用户级扩展都激活失败啦！？

我就知道，我是 Windows 系统，之前因为我的 C盘 太满了，我通过符号链接 mklink，把大量的缓存文件都移到了 E盘。

我的 `C:\Users\<user>\.vscode` 是一个指向 `E:\CAppData\.vscode` 的目录符号链接。

PowerShell 能正常进去，但 Node/libuv 对它做 stat 会返回 EPERM。

而 VS Code 的扩展宿主就是一个 Node 进程，读不到这个路径，扩展就激活不了；Jupyter 扩展根本没启动，Select Kernel 自然是空的。

## 确认原因

我先去看日志。

VS Code 的日志目录通常在 `%APPDATA%\Code\logs` 下，按时间找到最新的那次窗口，去找 `exthost.log`。

然后搜 `EPERM` 或者 `failed due to an error`。

再做一次 Node 侧的对比实验：

```js
const fs = require('fs')

const link = `${process.env.USERPROFILE}/.vscode`
const target = 'E:/CAppData/.vscode'

for (const p of [link, target]) {
  try {
    fs.statSync(p)
    console.log('STAT OK', p)
    const entries = fs.readdirSync(p)
    console.log('READDIR OK', p, entries.length)
  } catch (err) {
    console.log(err.code, p)
  }
}
```

好的，`C:/Users/<user>/.vscode` 报 EPERM，`E:/CAppData/.vscode` 一切正常。

再用 PowerShell 确认它的链接类型：

```text
Get-Item (Join-Path $env:USERPROFILE '.vscode') | Select-Object FullName, LinkType, Target
```

ok，`LinkType` 显示 `SymbolicLink`，果然是符号链接的问题。

## 修复

知道原因，修复起来就很简单了，直接把符号链接换成目录联接就行

目标目录不动，只换掉用户目录下这个入口。操作前先退出 VS Code。

```text
$p = Join-Path $env:USERPROFILE '.vscode'
$target = 'E:\CAppData\.vscode'

# 先确认目标目录真的存在，再动链接
Test-Path $target
(Get-Item $p -Force).Delete()
New-Item -ItemType Junction -Path $p -Target $target
```

强调一下：`.Delete()` 删除的只是链接本身，`E:\CAppData\.vscode` 里的扩展文件是不会少。

换成 Junction 之后，同样的 stat 就不再报 EPERM，扩展宿主能正常读目录。

## 结果验证

先看链接类型：

```text
Get-Item (Join-Path $env:USERPROFILE '.vscode') | Select-Object FullName, LinkType, Target
```

`LinkType` 变成 `Junction`。

再用 Node 复跑上面的脚本，三项都通过：`STAT OK`、`READDIR OK`，扩展目录能读出 35 个条目。

然后看 VS Code 自己能否正常识别扩展：

```bash
code --list-extensions --show-versions
```

能正常列出 `jupyter@2025.9.1` 这些扩展，说明扩展宿主已经恢复读取能力。

再回到内核层：用 jupyter_client 按 kernelspec 名字启动内核，执行一个单元，返回 `ok`。

最后，重启 VS Code 之后需要自己点一次，果然列表里出现所以内核。终于搞定了~



## 经验总结

为了节约 C盘 空间，把 C盘 的文件放在 E盘，再靠链接指过去，看着很方便，但其实还是暗藏很多雷的。

之后重装系统、迁移目录、换一台机器，都可能再遇到同一种 EPERM。

以后遇到这类扩展的问题，可以优先考虑是否是符号链接的问题。

不过排查思路也值得记录，遇到扩展整体不工作的问题，可以直接去看 `exthost.log`，日志里的 EPERM 可以直接定位的问题原因。
